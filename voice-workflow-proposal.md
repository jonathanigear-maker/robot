# Voice, Interaction and Behaviour Workflow Proposal

## Project purpose

The robot is intended to **independently live in the house and gradually become a member of the family** rather than being only a voice assistant on wheels.

Its core instructions, shared by both the local LLM and the OpenAI API, should reflect that purpose: participate naturally in household life, interact with people and cats, help when appropriate, entertain, explore, look after itself, and act independently when appropriate while keeping physical safety deterministic.

## First development goal: desk-bound social interaction

Before powering the drive motors, concentrate on making interaction feel natural while the robot sits on the desk.

Initial milestone: hold a natural face-to-face conversation in which the robot recognises/tracks the person, listens, thinks, responds, blinks, changes gaze, and uses subtle arm/head movement to communicate attention and personality.

Start with four interaction states:

- IDLE
- LISTENING
- THINKING
- SPEAKING

Add expression/reaction states later, for example CURIOUS, AMUSED, CONFUSED and SURPRISED.

Human-like behaviour should mostly be generated by a deterministic animation/expression controller, with small random variations in timing and movement. The AI selects the communicative intent; it should not command individual servo movements.

Examples include natural/random blinking, small gaze shifts, briefly looking upward or away while thinking, slight angular/head tilts, returning gaze to the speaker, and occasional subtle emphasis movement while speaking.

The touchscreen eyes provide gaze and eyelid animation. The HuskyLens provides face detection/recognition/tracking. The NeoPixel mouth should react to the actual outgoing speech audio like an amplifier/VU display.

The NeoPixel eye rings should primarily have **practical uses**, not be generic emotion indicators: desk/task lighting, illuminating a face when vision is too dark, illuminating an object being inspected, game hardware, and later local work/floor lighting.

## Local listening and command path

ReSpeaker -> Vosk -> local interpretation -> robot capability.

Keep Vosk loaded for fast local speech recognition. Routine commands should not require a cloud connection. Prerecorded WAV responses can provide fast, consistent responses for common actions.

A small local LLM can sit above Vosk to interpret less exact wording, decide whether speech is directed at the robot, extract intent/arguments, and make lightweight household/behaviour decisions.

The local model should run as one shared service rather than loading separate copies for voice, behaviour and other ROS nodes.

### Candidate local models

Models to benchmark on the Raspberry Pi 5:

- SmolLM2-360M-Instruct: https://huggingface.co/HuggingFaceTB/SmolLM2-360M-Instruct
- Qwen3-0.6B: https://huggingface.co/Qwen/Qwen3-0.6B
- llama.cpp runtime: https://github.com/ggml-org/llama.cpp

Start with a quantised GGUF build of SmolLM2-360M-Instruct through llama.cpp, then compare Qwen3-0.6B for decision quality, RAM use and latency. The small model is not expected to replace OpenAI; its job is quick local interpretation and simple decisions.

## OpenAI conversation mode

A local decision or explicit conversation request opens the OpenAI Realtime/voice connection. During cloud conversation, route microphone audio to OpenAI and pause/ignore normal Vosk transcription as appropriate, while keeping the local recogniser/model loaded.

The robot's purpose/personality instructions should also be supplied to OpenAI so local and cloud behaviour feel like the same robot.

Python/ROS remains responsible for opening/closing connections and executing capabilities. The model requests high-level actions; it does not directly drive hardware.

After a configurable inactivity period, close the cloud session and return to local operation.

## Robot voice character and audio processing

The current cloud voice uses OpenAI Live with the `ballad` voice, but the raw voice is deliberately post-processed on the Raspberry Pi so Robot keeps a natural, friendly speaking performance while gaining a recognisably synthetic character.

The current output signal chain is:

```text
OpenAI Live (ballad, 24 kHz mono PCM)
    |
    v
Python robot_effect()
    |-- 500 Hz sine carrier (65%)
    |-- 750 Hz sine carrier (35%)
    |-- dry voice mix: 0.75
    |-- modulated/robot mix: 0.35
    |-- output gain: 2.0
    |
    v
SoX pitch shift: +800 cents
    |
    v
ReSpeaker playback / speaker
```

The Python effect is a deliberately mild two-carrier ring/amplitude-modulation effect rather than a full replacement of the voice. For each 16-bit PCM sample, two sine carriers are generated at 500 Hz and 750 Hz, mixed 65/35, and multiplied with the speech sample. The modulated component is then mixed back with the original dry speech. This preserves intelligibility and much of Ballad's natural timing and expression while adding a metallic/electronic texture.

Current constants in `robot.py`:

```python
CARRIER_1_HZ = 500
CARRIER_2_HZ = 750
DRY = 0.75
ROBOT = 0.35
VOLUME = 2.0
```

Very quiet samples (absolute amplitude below 250) bypass the modulation and are only gain-adjusted. This avoids unnecessarily modulating near-silence/background samples. The result is clamped to the signed 16-bit range before being sent to SoX.

SoX then applies `pitch 800`, i.e. a pitch shift of +800 cents (eight semitones). The combination was chosen by listening rather than as a mathematically optimal setting: the design goal is a **friendly, understandable robot voice**, not a harsh classic vocoder effect.

Important implementation detail: `robot_sample_position` is maintained across incoming audio chunks. This keeps the modulation carrier phase continuous between streaming chunks instead of restarting the sine waves at every packet, which could introduce discontinuities/clicks.

When tuning the voice, change one element at a time. Carrier frequencies and the `ROBOT` mix mainly affect the metallic character; `DRY` controls how much natural voice remains; the SoX pitch value changes the perceived character; and `VOLUME` is output gain and should not be used as a substitute for speaker/amplifier volume control because excessive gain will hit the 16-bit clamp and distort.

The intended hardware path is the ReSpeaker XVF3800 feeding its amplified speaker output. A small enclosed 4 ohm / 5 W speaker is planned. Final volume should preferably be controlled at the playback/hardware mixer stage where available, leaving the voice-effect mix itself stable.

## Web/current-information workflow

When current information is needed, the robot can offer to search rather than guessing. After permission, it can announce the search, use the appropriate OpenAI web-capable workflow, return the result to the conversation, and speak a concise answer.

Permission and capability rules should also be enforced in Python rather than relying solely on model instructions.

## Shared robot capabilities

Both local and cloud intelligence should call the same constrained capability layer, for example:

- look_at(person)
- set_light(...)
- get_robot_state()
- open_gripper()/close_gripper()
- move_arm(...)
- start_game(...)
- later: go_to(location)

Safety limits and low-level motion remain outside the LLM.

## Interactive games and personality

Games are an early desk-bound development target because they exercise perception, controls, expression, speech and movement without needing the drive motors.

Available interaction hardware includes four front buttons, two colour-changing potentiometers, two touchscreen eye displays (each usable as a large button), NeoPixel eye rings, NeoPixel mouth, arm movement, HuskyLens, voice/ReSpeaker and the mounted laser.

Potential games include Simon/memory, reaction games, touchscreen choices, two-player potentiometer games, voice quizzes/20 Questions, object-finding games, and a robot version of the classic **useless box**. The useless-box game can use escalating/random reactions: notice a button press, look at the button, look at the person, reluctantly reset it with the arm, and optionally comment. Face recognition allows reactions to the person who keeps doing it.

The laser can eventually support controlled cat play, but actual laser aiming/activation must be governed by deterministic safety logic rather than unrestricted AI control.

## ROS architecture

ROS 2 becomes the robot's internal communications layer. One Arduino gateway node should own the Pi-Arduino serial connection; other ROS nodes communicate through topics/services/actions rather than opening the serial port themselves.

Likely nodes/components include:

- audio / Vosk
- local LLM service
- interaction / behaviour state
- OpenAI voice manager
- HuskyLens perception
- expression controller
- eyes
- Arduino gateway
- arm controller
- robot monitor/dashboard

Arduino remains the low-level hardware controller for fast/deterministic I/O, displays, servos, buttons, potentiometers and suitable sensors. ROS/Pi handles higher-level state, AI, perception and planning.

## MoveIt and arm plan

MoveIt 2 will eventually provide model-based arm control rather than reasoning in raw servo positions.

Planned sequence:

1. Install Ubuntu 24.04 ARM64 and ROS 2 Jazzy on a separate SD card/SSD while preserving the working Raspberry Pi OS card.
2. Create the robot/arm URDF with accurate link lengths, joint limits and sensor locations.
3. Publish measured servo positions as joint states.
4. Test the virtual arm in RViz.
5. Configure MoveIt 2 and test planning without physical movement.
6. Bridge planned trajectories to the Arduino.
7. Test one real joint, then the full arm and gripper.
8. Expose safe high-level arm capabilities to the behaviour/local/OpenAI layers.

Actual servo feedback should be used rather than assuming commanded position equals real position. Feedback can be sampled at a sensible rate rather than continuously hammering the servo bus.

## Longer-term voice/robot flow

```text
ReSpeaker
    |
    v
Vosk --------> local commands
    |
    v
Local LLM / behaviour
    |             \
    |              -> OpenAI when richer conversation/reasoning is needed
    v
Robot capabilities
    |
    v
ROS
    |
    +--> expression / eyes / voice
    +--> MoveIt / arm
    +--> Arduino / hardware
    +--> later Nav2 / navigation
```

The immediate objective is not autonomous driving. It is to make the stationary robot feel attentive, responsive and enjoyable to interact with, while building components that remain useful when navigation is added later.
